# 智能体驱动的自动向量化优化系统设计报告

## 摘要

本报告记录"智能体驱动的自动向量化优化系统"的总体设计、模块划分、单次优化任务的执行机制，以及面向 TSVC 基准集十个人工选择内核的实验与分析。系统以一个大语言模型（LLM，DeepSeek）为核心分析者与代码生成者，将向量化机会识别、等价改写生成、正确性验证、向量化确认与性能对比等环节交由固定的确定性工具流水线闭环执行，从而实现对"编译器无法自动向量化"的函数进行无人值守的自动优化探索，并在此过程中沉淀可复用的向量化经验。实验结果显示，在十个目标内核中，七个在无人值守的运行中达到至少 1.15 倍的加速比（最高 vdotr 7.38 倍、s453 5.47 倍），两个内核虽能被改写为可向量化形式但性能无收益（作为"no-gain"留存的负例），一个内核确有不低于 1.45 倍的已有实现但其自动化复现尚不稳定。报告同时讨论了该方案的能力边界、测量方法学上的局限以及后续的改进方向。

## 一、引言

SIMD（单指令多数据）向量化是现代处理器提升数值计算吞吐量的主要手段之一，主流编译器都会在较高优化级别下尝试对热点循环进行自动向量化。然而自动向量化受制于编译器对循环结构的保守分析：循环携带的数据依赖、浮点归约的重结合规则、控制流的非结构化表达、指针别名的不确定性等障碍，都会让向量化器放弃变换，即便该循环在语义上存在一个等价的、可向量化的形式。手工改写这类代码通常需要深厚的编译与数值分析经验，代价高且难以规模化推广。

近年来，以大语言模型为代表的学习方法开始被引入编译优化领域，已有研究探索利用 LLM 直接生成向量化代码或改写待优化循环（例如 LLM-Vectorizer、VecTrans 等）。这类方法的共同难点在于：模型生成的代码是否正确、是否真的被编译器向量化、是否带来实际性能收益，都需要可靠的验证手段，而模型本身无法自证。本项目正是围绕这一问题展开：设计并实现一个"智能体驱动的自动向量化优化系统"，其核心思想是把 LLM 放在一个由确定性工具构成、阶段固定、闭环反馈的优化管线中。LLM 只负责"分析"与"生成"两类需要推理的任务，其余所有涉及事实判断的环节——编译是否通过、运行结果是否正确、循环是否被向量化、加速比是否达标——均由工具以可复现的方式裁决，任何一道闸门失败都会产生结构化反馈，引导模型在下一轮做针对性修正。

系统以 TSVC（Test Suite for Vectorizing Compilers）基准集为对象。TSVC 是一套经典的向量化编译器评测集，其来源可追溯到 Maleki 等人发表于 PACT 2011 的工作《An Evaluation of Vectorizing Compilers》，本仓库中的版本取自 LLVM 官方测试套件 llvm-test-suite。我们从中选取了十个在 clang `-O3 -march=native` 下无法被自动向量化的内核，在本地 C 实验场（vec-lab）中为每个内核建立"原始实现（orig）＋待实现优化版（opt）"的可编译、可运行、可度量框架，交由智能体自动完成从障碍分析到经验沉淀的完整优化闭环。截至本报告撰写，系统已实现对单内核的无人值守优化：在终端执行 `node src/cli.js s211` 即可自动完成上述全过程，无需任何对话引导。

## 二、相关工作简述

自动向量化是编译器经典优化问题，学术界与工业界对其中的依赖分析、重排序、循环变换已有长期研究，TSVC 即用于系统评测此类能力。由于编译器受限于保守静态分析，跳出其变换框架的途径之一是由具备领域知识的主体对源码施加等价改写，这正是本项目的立足点。近年出现的 LLM 辅助向量化工作（如 LLM-Vectorizer、VecTrans）表明，大模型能够依据源码与编译诊断产生有一定命中率的向量化候选，但它们普遍面临正确性验证与候选规模控制的挑战，其中部分工作借助 Alive2 这类翻译验证工具进行形式化证明，且受限于 SMT 求解复杂度，验证通过率并不理想。本项目在正确性保障上选择了与形式化验证互补的动态验证路线——以确定性输入上的逐元素容差比对作为正确性裁决标准，以编译器的向量化记录与实测基准作为向量化与性能裁决标准。关于利用 Alive2 对生成代码进行翻译验证的尝试与教训，我们在仓库文档 `docs/USE_ALIVE_2.md` 中有独立记录；其基本结论是 alive-tv 在不加调整的情况下对含循环的翻译验证会产生 SMT 求解复杂度爆炸，该方法目前未引入本系统，但仍是值得后续投入的方向（详见第七章）。

## 三、系统架构

### 3.1 总体设计思想

系统的总体架构可以概括为三个层次：底层是一个被测对象与测量框架——C 实验场 vec-lab，它把每个目标内核组织成可独立编译运行、输出结构化指标的最小工程；中间层是一组确定性本地工具，负责编译、运行、解析编译器的向量化诊断记录、计时基准、源码改写与闸门汇总；上层是智能体主控 driver，它按照固定的阶段编排上述工具，并在分析（analyze）与代码生成（generate）两个环节调用 LLM。三者通过两个"接口约定"彼此解耦：其一是 vec-lab 入口程序约定在标准输出打印一行包含正确性与性能字段的 JSON，其二是提示词模板与解析器约定 LLM 返回可被机器抽取的 JSON 或代码围栏。

这一分层的关键决策在于，把"LLM 可能出错的环节"与"机器必须绝对可靠的环节"彻底分离。验证与度量全部由确定性工具承担，LLM 不拥有工具调用能力、也不需要自证其正确性；它的每一次产出都会被同一套、与生成路线无关的四道闸门强制检验。如此，模型的非确定性只会影响候选的质量分布，而不会影响判定的正确性，从而保证整条无人值守管线的结论可信。下面分别介绍三个层次的内部设计。

### 3.2 C 实验场 vec-lab

vec-lab 是存放被测内核及其测量框架的实验场，它从 TSVC 中挑选了十个 clang 无法自动向量化的内核，按 TSVC 分类分别覆盖了 ControlFlow、StatementReordering、NodeSplitting、LoopRestructuring、Packing、Equivalencing、InductionVariable 与 ControlLoops 等类别的典型向量化障碍。每个内核在 `kernels/<name>.c` 中同时提供忠于 TSVC 原版的 `_orig()` 实现与待实现的 `_opt()`，其头部注释记录了该内核的障碍与建议优化方向，作为给 LLM 的人工提示。实验场公共框架 `common.c/common.h` 提供全局数据、确定性初始化、快照与容差比对、计时与 JSON 报告等能力。

在数据组织上，vec-lab 有意采用了与 TSVC 原版不同的布局：原版通过结构体与 `TYPE *const` 指针访问全局数组，其别名分析失败会把不少本可向量化的函数误判为不可向量化；实验场改为直接引用全局数组以消除该伪障碍，使"orig 不可向量化"的基线诊断更准确。全局数组包括五个一维数组 `a` 至 `e`（长度 LEN，默认 32000）、三个二维数组 `aa/bb/cc`（LEN2×LEN2，默认 256×256）、一个一维缓冲 `xx_buf` 及指向它的别名指针 `xx/yy`（仅 s421 需要制造别名反依赖），外加一个归约结果标量 `lab_result`。

数据初始化是确定性的：初始化函数以一个固定种子（42）驱动线性同余生成器，把五个一维数组填充到 [−1,1) 区间以混合正负样本，二维数组填充为固定常量，随后把别名指针复位指向缓冲。由于 orig 与 opt 始终从同一份输入出发，二者输出的逐元素比较才有意义。为了给循环提供有实际优化意义的运行场景，公共框架还提供内核专属的数据特化钩子 `lab_prepare`，例如对 s482 在初始化后把数组 b 整体抬高 2.1，使循环体内的提前退出条件恒不成立，从而让"含 break 的循环"在全长遍历的语义下被测试。

正确性裁决由快照与比对实现：优化入口在同一进程内先运行 orig 作为参考并保存快照，再重新初始化、运行 opt，然后以相对容差公式逐元素比对快照与当前数据，返回不一致的元素个数。除 vdotr 因浮点归约的重结合允许误差外，其余内核均要求位精确（容差为 0）；vdotr 则按数据类型自动选择 1e-9（double）或 1e-5（float）的容差。为便于智能体诊断，比对器会在不一致时输出至多八个样本，指明发生差异的数组名、下标、期望值与实际值。正确性之外，公共框架以"六个数组之和加归约结果"的校验和作为输出指标，并以一个不会被优化的哑函数防止编译器删去"看起来无用"的热循环。

入口层按被测对象与优化形态拆分为基线入口与优化入口：基线入口只运行 orig，输出单行 JSON；优化入口则在内部完成"orig 作参考、快照、opt、比对"的完整流程并输出单行 JSON，其 `status` 字段在占位未实现、运行出错、运行正常但结果不一致、全部一致等情形下取不同取值。为了在 `_opt()` 尚未实现时工程仍可编译链接，优化入口文件内以 `#ifndef HAVE_<大写K>_OPT` 提供了一个返回 1 的占位实现；当智能体把真实实现写入内核文件后，编译时须追加 `-DHAVE_<大写K>_OPT` 以屏蔽占位、链接真实实现。每一入口只链接一个内核（entry＋common＋对应 kernels 文件），保证 clang 的优化诊断与计时都只针对目标内核。以上约定构成了 node 端工具与 C 端框架之间的稳定协议，也是自动化得以成立的基础。

### 3.3 确定性工具层

中间层工具把智能体需要的"事实获取"全部封装为可复现的子程序。编译运行工具驱动 clang 按固定的 `-O3 -march=native -DTYPE=double -I.` 旗标构建基线或优化入口的可执行文件，并在优化构建时自动附带对应的 HAVE 宏；它同时负责解析入口输出的单行 JSON。向量化诊断工具解析 clang 以 `-fsave-optimization-record` 产生的优化记录 YAML，把其中的记录规整为结构化对象，随后按函数与 pass（loop-vectorize）过滤，提取向量化"Passed/宽度"、"Missed 原因"等关键信息，并附带一个面向 intrinsic 路线的、从指令混合记录中探测 SIMD 指令证据的启发式函数。由于优化记录可能很长，工具会对其进行限行摘要，既保留诊断要点又控制进入提示词的 token 开销。

基准工具对某内核的基线与优化可执行文件分别启动独立进程各跑多次（默认 7 次），取每次的 CPU 时间并汇总为最小值与中位数，以"orig 最小时间除以 opt 最小时间"作为加速比指标。之所以采取分进程多次计时，是为了让 orig 与 opt 处于同等冷启动条件下，并用最小值或中位数抑制单次抖动。源码改写工具负责把 LLM 产出的候选函数以带标记的代码块形式写入（或替换）`kernels/<name>.c`，并保证同一函数始终只有一份实现、失败轮次结束后能被整体还原。闸门汇总工具把一次尝试在编译、运行正确性、向量化确认、性能四项上的结果聚合为 pass/fail 判定，并把失败信息组织成面向 LLM 的诊断文本——例如在性能闸门失败时提示"这类内核通常访存受限，若向量化后反而变慢，多半是改写引入了额外的整数组往返、翻倍了内存流量，应尽量用代数代入消去依赖、在单遍循环中只读旧值"。该提示不是模板字符串，而是把项目在失败调试中反复得到的经验沉淀进了反馈生成逻辑。

### 3.4 大模型集成与提示词设计

LLM 层负责与 DeepSeek（OpenAI 兼容接口）通信、组装提示词以及稳健地解析输出。客户端在收到空内容或 `finish_reason=length`（回复被输出预算截断）时自动重试，并在重试时把预算按倍数放大（上限封顶）并附加"保持简短而完整"的提示，以对抗推理型模型把大量 token 消耗在内部推理上、导致正式回答截断的问题。提示词模块从 `prompts/` 目录加载模板并填充 `{{占位符}}`；解析模块实现了健壮的输出抽取——以括号配平扫描从任意夹杂前言的文本中提取 JSON 对象、从文本中提取第一个代码围栏、校验生成代码确实定义了目标函数——并对模型常见的"JSON 未闭合""缺少必填字段"等失败给出带上下文的报错。

提示词分分析、生成、反思三类，且生成按候选路线拆分出三个模板。分析模板要求 LLM 严格依据给出的内核源码与 orig 的 clang 诊断记录作答，禁止凭对 TSVC 的记忆重建函数，输出结构化的 JSON，包括：向量化障碍的精确陈述与其类别（真依赖/反依赖/控制流/归纳变量/归约/别名/其他）、所属 TSVC 类别、一句话策略、可执行的分步变换计划、风险与性能注意事项，以及按可行性排序的候选路线建议。生成模板则区分了等价改写（rewrite）、指令注记（pragma）与手写 SIMD 内建函数（intrinsic）三种路线：改写模板强调消除循环携带依赖、保持外层重复结构与往返次数不变、大缓冲必须用 static、逐位精确（归约类除外）、以及"先读旧值到局部变量再写"等硬性规则；pragma 模板给出按障碍择用的指令清单，例如结构可向量化但被 cost-model 拒绝时使用 `#pragma clang loop vectorize(enable)`，编译器诊断建议循环分发时使用 `distribute(enable)`，浮点归约需要重结合时使用 `#pragma omp simd reduction`；intrinsic 模板则面向自动向量化稳定拒绝但确有可能手写收益的情形，给出 AVX2 双精度 intrinsics 的容量、越界防护与数值一致约定。反思模板在某一闸门失败后以极低的 token 预算请 LLM 给出根因、下一步动作与具体修改点，其输出被拼接到下一轮生成的反馈历史中。设计上，生成器每一轮只产出一个候选，通过"基于历史反馈做小步修正"而非大爆炸式多候选，来同时控制 token 成本与调试复杂度。

### 3.5 智能体主控与阶段管线

智能体主控 driver 把上述要素编排为一条固定阶段、带反馈回路的优化管线。对单个内核，driver 先建立实验工作区、备份内核原始源码并初始化运行状态，随后进入基线阶段：编译并运行 orig、收集其对 loop-vectorize 的诊断记录，确认 orig 确实未被自动向量化，把其运行时间与 remark 摘要作为后续分析与对比的底数。接下来调用 LLM 分析，得到障碍、类别、策略、变换计划与推荐路线；driver 依据该推荐（或命令行强制指定）生成一条确定性的路线调度：默认的首选路线（通常是 rewrite）获得除去兜底份额外的全部尝试次数，每个后续兜底路线各分得固定次数，从而避免实证上对约半数内核有效的改写路线被"饿死"。

随后进入最多 MAX_TRIES 轮的尝试循环。每一轮按当前路线选择对应的生成模板，把 orig 源码、baseline remark、分析结果、检索到的相似经验、此前全部反馈与上一次候选代码一起组装进提示词，请 LLM 生成完整的 `int <kernel>_opt(void)`。候选代码先被逐字节哈希，若与先前某一失败尝试完全相同，driver 会判定模型忽略了反馈，转而提高采样温度并附加警告重新请求一次结构不同的实现。候选通过后即被写入内核文件，然后依次接受四道闸门：编译闸门要求候选能在附加 HAVE 宏的前提下通过 clang 编译；正确性闸门要求优化入口运行正常且逐元素不一致数为 0；向量化确认闸门重新以保存优化记录的方式编译候选，要求诊断中出现针对该函数的 loop-vectorize Passed 记录且向量化宽度不小于 2；性能闸门要求分进程 best-of-N 测得的加速比达到设定阈值（默认 1.15）。任何一道闸门失败都会把当前候选标为对应失败类型，生成结构化反馈追加进历史，并视配置调用一次低成本的反思，然后进入下一轮。若四道闸门全部通过，本轮候选即被采纳：内核文件保留优化实现，driver 导出 result.json、向 results.csv 追加一行并把一条成功经验写入经验库。若预算耗尽仍未达标，driver 会把内核文件恢复为基线备份、标记失败并同样记录经验，从而保证仓库内不残留未达标的实现。运行状态在每个尝试之后都会持久化，既支持中途断点续跑，也为审计留下了完整轨迹。

为覆盖"正确且被向量化但加速比不达标"的情形，系统提供了 no-gain 留存模式：在该模式下，正确且向量化但低于阈值的候选不会立即判负，而是记住其中最优者，在预算耗尽时把它重新写回内核文件并标记为 `ok-nogain`，作为诚实的实证结论保留。这一机制使系统既能报告正收益，也能区分"方法不适用"与"系统失败"。

### 3.6 经验记忆与运行产物

经验记忆模块把每次优化的结论以结构化形式追加进 `memory/experiences.json`，记录内核、类别、障碍类型、障碍陈述、策略、变换计划、陷阱提示以及结果（是否成功、加速比、向量化宽度、对应候选文件）。在开始新内核的尝试循环前，driver 会按类别与障碍类型检索至多四条最相关的既有经验（成功经验权重更高），把它们以紧凑文本形式并入生成提示词。该机制使得系统在不同内核之间实现知识的横向迁移——例如"先读旧值到局部变量、单遍消除依赖"这一在多个 StatementReordering 内核上验证过的模式，能够在新内核首轮就被模型参考，而不是从零开始探索。

运行产物集中在每个内核自己的 `experiments/<kernel>/` 工作区：`state.json` 记录完整运行状态（基线指标、分析、每一尝试的闸门结果与反馈）、`result.json` 导出最终结果、`attempt_<n>.c` 与 `candidates/<route>_<n>.c` 留存每次候选代码、`diag_orig.opt.yaml` 与 `diag_opt.opt.yaml` 保存原始与优化实现的向量化诊断证据、`kernels_orig.c` 保存原始源码备份；全内核的汇总行追加在 `experiments/results.csv`。这些产物同时服务于审计、复现与报告生成。

### 3.7 鲁棒性设计与若干设计决策

无人值守系统必须容忍模型输出的多种非理想形态，本系统的鲁棒性处理贯穿三层：在接口层，解析器以括号配平扫描容忍前言之类噪声，并明确报告"JSON 未闭合""缺少字段"等失败模式；在客户端层，针对截断回复实行预算放大与简洁性引导的重试；在编排层，对字节级重复的候选强制换方案，对反思产出为空的情形显式标注"本轮无可用引导"而绝不静默吞掉，让下一轮生成器知道历史轮次是否真正被反思引导。此外，分析阶段的 JSON 调用失败会重试至多三次，生成阶段对代码形态的校验失败也会重试，保证单点偶发故障不直接中断整轮任务。

有两个设计决策值得说明。其一是系统没有给 LLM 引入工具调用（function/tool calls）能力：理由在于本架构中"验证与获取信息"已由 driver 用确定性工具完成，且每次生成后都强制跑同一套闸门，模型并无自证正确性的必要；引入工具调用会带来多轮状态、更多失败面与更高成本。当需要向模型补充现场信息时，优先以确定性方式把更丰富的上下文（如对应循环的反汇编、更多 remark）直接喂进提示词。其二是候选多样性以增量而非重构的方式落地：rewrite 被保留为默认首选，只有当 analyze 依据障碍信号给出不同推荐或改写连续失败时，才沿 pragma、intrinsic 等路线向上切换，且四条闸门对所有路线完全一致，不因路线不同而放宽判定；intrinsic 路线的"向量化证据"则通过指令混合中是否出现 SIMD 指令来补充确认。

## 四、实验方法学

实验的目标对象是 TSVC 中十个在 clang `-O3 -march=native` 下无法自动向量化的内核。被测对象及其向量化障碍如下：s453（InductionVariable，浮点归纳变量）、vdotr（ControlLoops，浮点归约禁止重结合）、s212 与 s211（StatementReordering，跨迭代反依赖/真依赖）、s241（NodeSplitting，相邻跨迭代真依赖）、s292（LoopRestructuring，回绕归纳变量）、s482（ControlFlow，break 提前退出）、s1161（ControlFlow，if/goto 互斥分支）、s341（Packing，写位置依赖前缀计数）、s421（Equivalencing，yy/xx 指针别名反依赖）。

所有测量均在 `clang -O3 -march=native -DTYPE=double` 下进行，每内核只编译链接自己的入口与公共框架。正确性以优化入口同进程内"先跑 orig 作参考、再跑 opt、逐元素容差比对"的方式裁决：不一致数为 0 即通过，其余内核要求位精确，仅 vdotr 允许 1e-9（double）的归约重结合误差。性能以基线与优化可执行文件各自分进程运行 7 次、取最小值计算加速比 `speedup = min(orig)/min(opt)` 的方式度量，中位数一并记录；需要说明的是，优化入口内 opt 在同进程、暖缓存条件下测得，因此加速比存在系统性乐观偏差，但对智能体的接受决策而言这是安全方向的偏差——宁可高估也不漏判。实验机器为搭载 AMD Ryzen 7 5800H（AVX2＋FMA）的 Windows 11 主机，编译器为 clang 23.1.0，一维数组长度 LEN=32000，外层迭代次数 NTIMES=2325（部分内核在 orig 中以 2 倍或 10 倍次数重复以保证计时稳定）。最终判定准则为：`ok` 需同时满足正确、clang 实际向量化（诊断出现 Passed 且宽度不小于 2）与加速比不低于 1.15；`ok-nogain` 为正确且向量化但加速比低于 1.15 并在留存模式下被保留。

| s212 | StatementReordering | ok | 2.38 / 2.28 | 4 | 1 |

### 5.2 正收益内核的分析

归纳变量类内核以 s453 为代表。其原循环维护一个以 2.0 步进累加的浮点归纳变量 s，并令每个元素等于 `s*b[i]`。由于浮点加法不满足可交换结合律，向量化器无法把该归纳变量安全地转换成解析形式，于是循环携带的标量依赖使循环整体被拒绝。模型的改写把它替换为整数的解析式 `a[i]=(TYPE)(2*(i+1))*b[i]`——由于步长为精确的 2，该序列中的每个值在 double 范围内都能被整数精确表示，改写不改变任何数值结果。依赖消除后循环变成单遍、无额外访存的纯元素操作，一次尝试即命中 5.47 倍收益。这是"逆强度削减"思想在浮点归纳变量上最直接的运用，也印证了该类障碍一旦识别准确、改写收益可观。

浮点归约类内核 vdotr 的障碍在于：默认的 IEEE 浮点语义禁止对累加顺序进行重结合，而向量化内核对归约的展开本质上会改变结合顺序，因此 clang 不自动向量化该归约。可行的方向是显式允许该归约被重结合——既可以用 `#pragma omp simd reduction` 类的指令让编译器获得许可，也可以把归约改写为多路部分累加再合并。保留实现通过在热点循环上施加显式向量化指令并限定宽度为 4，使 clang 最终以 AVX 的 4 路 FMA 融合乘加完成归约，其结合顺序的改变落在 1e-9 的容差内。该内核取得全场最高的 7.38 倍收益，说明对受语义约束的归约内核，关键在于"授权"而非"改变结构"。值得注意的是，候选多样性框架在该内核上的多次尝试（三种路线均已触及、最终在三次尝试内达标）体现了"一条路走不通时切换路线"对提高成功率的实际价值。

语句重排与跨迭代依赖类内核（s212、s241、s211）共享同一种本质：循环体内部既有写数组某位置、又在随后的语句或相邻迭代中读取该位置的旧值，形成写后读或真依赖链，向量化器无法证明"旧值先读"的安全。对此类问题的通用解是让模型把需要用到的旧值先读入普通局部变量，再执行写操作。s212 中 `b[i] += a[i+1]*d[i]` 读取的是将在下一迭代被覆写的 `a[i+1]`，把 `a[i]` 与 `a[i+1]` 的旧值先行保存后，语句重排即消除了反依赖；s241 中 `b[i]` 同时依赖本迭代新写的 `a[i]` 与旧值 `a[i+1]`，先把两个旧值读到局部量、再按原顺序更新 a 与 b 即可打断相邻跨迭代的真依赖；s211 则同时存在"读上一迭代刚写的新 `b[i-1]`"的真依赖与"读未写 `b[i+1]`"的反依赖，模型采用代数代入的方式把对该新值的引用等价展开，使循环体内只读取尚未被本循环写过的数据。这三类改写分别命中 2.38、2.15 与 1.74 倍收益，且 s212、s292 等内核仅用一次尝试即达成目标，说明"先读旧值、单遍消除依赖"这一模式具有很高的可迁移性，也正是经验记忆模块能够在不同内核之间复用的核心知识。

回绕归纳变量类内核 s292 的问题来自两个在下标序列末端取初值、随迭代逐步滚动的标量 im1/im2，向量化器面对这种环状索引依赖只能放弃。模型采用循环剥离：手工展开前两次迭代后，剩余迭代中 im1/im2 恰好退化为固定的 `i-1` 与 `i-2`，循环体变成对 `b[i-1]`、`b[i-2]` 的固定偏移访问，从而可以整体向量化。这一变换边界清晰、改动局部，一次尝试即获得 1.54 倍收益。控制流类内核 s482 的问题在于循环体内的数据相关提前退出（break），向量化器原则上无法用一条"未知长度"的向量路径表达提前停止。模型结合数据特化采用了扫描与计算两遍的思路：先在向量宽度粒度上扫描出首个违反退出条件的下标，再据此把主更新循环执行到该位置；借助公共框架把数据调整为使退出恒不发生的设定，两遍都退化为全长遍历的规整循环，最终 1.54 倍达标。

上述内核的共性在于：其障碍都能被一个结构上"可解释、可局部化"的源级变换消除，改写后循环保持单遍或少数几遍的访存模式，因此向量化带来的指令与带宽收益能够真正兑现。这也正是系统把等价改写设为默认首选路线、并把"避免引入额外整数组往返"写进生成提示词与失败反馈的缘由。

### 5.3 两个 no-gain 负例的机理分析

s1161 与 s341 与前述正收益内核形成鲜明对比：智能体在它们身上同样找到了正确且被 clang 向量化的改写，但实测均慢于标量基线，最终以 no-gain 形式留存。这两个案例不应被理解为失败，反而恰是系统价值的一部分——它能诚实地区分"无法改写"与"改写成功但无收益"两种情形，并用统一的闸门给出可复现的证据。

s1161 的原实现以 if/goto 构成两个互斥分支，标量版本每个元素只需执行其中一个可预测分支。模型的改写把 goto 结构化、分别对两个分支施加向量化，结果虽然被 clang 确认向量化（宽度 4），但向量化版本被迫对每个元素同时计算两个分支再做比较，并用两次掩码分别写回数组 a 与 b，指令数与访存量近乎成倍增长，实测只有约 0.85 倍。该现象的本质是"谓词化双写"：向量化宽度的收益被成倍的冗余计算与写回吞没。在语义不变的前提下，等价改写、pragma、intrinsic 三条路线都难以改变这一结构性代价。

s341 则是"写位置依赖前缀计数"的压缩（packing）内核：结果写位置 j 是此前满足条件元素个数的累计，标量实现本就以单遍就地紧凑写高效完成；要向量化必须先额外完成谓词生成、前缀和求目标下标乃至散射写等辅助工作，这些辅助访存与指令开销超过向量化收益，三路线实测最优也只有约 0.78 倍。该案例说明，当标量算法自身已经是低访存的线性扫描而向量化需要引入"索引计算"等附加结构时，向量化未必划算。

这两例共同给出一个重要结论：自动向量化的价值不取决于"是否产生了向量指令"，而取决于向量化后指令与访存结构是否真的更优；一个具备正确性判定与真实计时的闭环系统，正是把这种看似反直觉的结论变成可验证事实的必要工具。

### 5.4 s421 复现不稳定问题

s421 属于第三种情形：内核确实可优化，但智能体的自动化复现不稳定。其障碍是 `yy=xx` 使两个指针指向同一数组，循环 `xx[i]=yy[i+1]+a[i]` 因此存在对自身旧值的反依赖，clang 的别名分析无法证明安全而拒绝向量化。解耦方法明确：先把旧值 `xx[i+1]` 拷入静态临时缓冲，再对更新循环施加 `__restrict` 与显式向量化指令，改写后可达约 1.45 倍收益，该实现保存在 `vec-lab/kernels/s421.c` 中并可稳定复现。问题在于自动运行时模型经常产出触发"cannot identify array bounds"诊断的指针写法——clang 无法推断其指针所指向数组的边界，从而拒绝向量化——在有限预算内往往只有少数轮次能命中正确形式。因此该内核的偶发失败记录反映的是"模型生成可靠性低"，而非内核本身不可优化。这一案例暴露了当前方案在指针/别名场景下的弱点，也提示后续应针对该障碍类型补充更强的检索与示例引导。

### 5.5 讨论与已知局限

首先需要客观看待测量本身的局限。计时基于 Windows 的 CPU 时钟，分辨率约 1 毫秒，对数十毫秒量级的内核存在百分之几的量化误差；尽管 best-of-N 取最小值/中位数已抑制大部分抖动，更精细的计时仍需更高分辨率的计数器。更重要的是，LEN=32000 时全部数组约 1.5MB，工作集基本驻留于三级或部分二级缓存，许多循环实际处于缓存带宽受限状态，标量版本本身已被 unroll 与 SLP 逼近带宽上限，因此 s211、s292 等访存型内核的向量化增益被压缩在 1.5 倍上下。若把数组规模提升到超出缓存、进入内存带宽主导的量级，向量化"更少指令、更高效访存"的优势通常会被放大，现有若干接近 1 倍的访存受限内核有望获得更可观的加速比——这是一条低成本、值得一试的后续实验路径。与多线程并行不同，SIMD 没有线程创建与调度开销，其收益主要受寄存器宽度、访存瓶颈与启动收尾段占比限制，因此数据规模对二者的影响机制并不相同。另外，`-march=native` 使所有产物与本机指令集绑定，换机需要重新编译并注明 CPU。

在方法边界上，当前的方案本质是"把源码改写成等价的、clang 能自动向量化的 C"，配以编译器诊断与模型分析，因此擅长消除或代入循环携带依赖、处理可解依赖的规整循环，而对"标量已被逼近最优的访存受限循环""cost-model 拒绝但结构已可向量化的循环""需要显式允许归约重结合的循环"以及若干结构性依赖，单纯等价改写的空间有限。候选多样性机制已在部分此类情形（如 vdotr 的指令注记、s341 的手写 SIMD）中证明了其价值，但也应看到其边界：对于谓词化双写或压缩类结构性代价，任何源级路线都难以逆转。此外，模型输出质量仍存在随机性，个别内核（如 s421）的首轮命中率不高，依赖多轮反馈修正；把相关经验、示例与更精确的现场信息（如反汇编）纳入提示词是提升可靠性的主要手段。

## 六、总结

本项目实现了一个以 LLM 为分析与生成核心、以确定性工具为验证与度量基础的自动向量化优化系统。在架构上，它通过 C 实验场、确定性工具层与智能体主控的分层解耦，把模型的非确定性隔离在候选生成一侧，而把正确性、向量化与性能的裁决完全交给可复现的闸门，从而在不引入人工干预的前提下对单个内核完成从障碍分析、改写生成、验证比较到经验沉淀的完整闭环。在实验上，系统在十个编译器无法自动向量化的 TSVC 内核中取得七个显著加速（其中两个超过 5 倍），正确留有两个 no-gain 负例，并为 s421 保留了一个稳定可达 1.45 倍的实现。这些结果验证了"LLM 提出变换、编译器与实测裁决"这一范式的可行性，也展示了负例分析对理解自动向量化收益边界的价值。

## 七、展望

后续工作可沿两条主线展开。其一是继续打磨候选多样性与可靠性：对指针别名、压缩等结构性障碍补充更充分的示例与经验检索，把分析阶段对障碍的刻画更细粒度地与路线预算挂钩，并在更大数据规模下重做测量以厘清访存受限内核的真实增益。其二是引入形式化验证以补强正确性保证：目前正确性以确定性输入上的容差比对为裁决，属于动态验证范畴；利用 Alive2 等翻译验证工具对改写前后的循环进行形式化等价性证明是一个诱人的方向。仓库中的调研记录表明，alive-tv 在未加调整时对含循环的翻译验证会因 SMT 求解复杂度而超时，即便在此方向上已有工作也往往只能证明少数比例的向量化候选；将循环展开、数组长度收缩等规模控制手段与按需触发、多级验证（先动态比对、再对关键候选做形式化）相结合，可能是让形式化验证落地为常态闸门的可行路径。此外，为十内核实验补充跨机器与多编译器的可移植性数据，也是完善该课题结论的后续工作。
